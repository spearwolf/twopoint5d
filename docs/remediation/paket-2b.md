  1. **`alignedAttributeSize.ts`** (intern, nicht in `public-api.ts`):
     ```ts
     export function alignedAttributeSize(size: number, dataType: VertexAttributeDataType): number
     ```
     Liefert `Math.ceil((size * bytes) / 4) * 4 / bytes`, mit `bytes` aus einer modullokalen `Record<VertexAttributeDataType, number>`: `float64: 8, float32: 4, float16: 2, uint32: 4, int32: 4, uint16: 2, int16: 2, uint8clamped: 1, uint8: 1, int8: 1`. Ergebnis: 32/64 Bit unverändert, 16 Bit auf eine gerade Zahl, 8 Bit auf ein Vielfaches von 4. JSDoc sagt in einem Satz, warum: WebGPU verlangt, dass jedes Attribut eines Vertex-Buffers auf einem Vielfachen von 4 Byte beginnt (bei Formaten ab 4 Byte) und die `arrayStride` ein Vielfaches von 4 Byte ist; three 0.185.1 wählt für jedes Attribut mit mehr als einem Wert ein Format, das auf ganze 4 Byte aufgerundet ist (`unorm8x4` für drei Bytes, `WebGPUAttributeUtils.js:538–548`).
  2. **Layout im Konstruktor von `VertexObjectBuffer`** (Zweig ohne Quell-Buffer, Schleife Z. 232–253): jedes Attribut belegt `alignedAttributeSize(attribute.size, dataType)` Elemente statt `attribute.size`; `dataType` ist der des Buffers (`buffer.dataType` für ein weiteres Attribut, `attribute.dataType` für das erste — das Array des Buffers entsteht mit dem Typ des ersten). `offset` bleibt die bisherige Summe, `itemSize` wächst um den ausgerichteten Wert. Damit ist jeder Offset × Elementgröße ein Vielfaches von 4, und `itemSize` × Elementgröße auch. Keine weitere Änderung an Accessoren, `copy()`, `copyArray()`, `copyWithin()`, `copyAttributes()`, `toAttributeArrays()`, `VertexObjectPool` (Resize): sie rechnen alle mit `itemSize` als Stride und `offset` aus dem Layout. Ein Inline-Kommentar an der Stelle sagt, warum ausgerichtet wird (WebGPU-Vertex-Layout; ohne Ausrichtung polstert three einen nicht interleavten Buffer bei jedem Update neu und kopiert dafür das ganze Array, `WebGPUAttributeUtils.js:202–222`). Die Polster-Elemente liest und schreibt kein Accessor; sie bleiben 0, solange niemand ganze Arrays hineinkopiert.
  3. **`initializeAttributes.ts`**: ein Buffer wird auch dann ein `InterleavedBuffer` (bzw. `InstancedInterleavedBuffer`) mit `stride = buffer.itemSize` und einem `InterleavedBufferAttribute(interleavedBuffer, attrDesc.size, 0, attrDesc.normalizedData)`, wenn er nur ein Attribut hat, dessen `size` kleiner ist als `buffer.itemSize` (also gepolstert). Bedingung: `attributes.length > 1 || size des einzigen Attributs !== buffer.itemSize`; der bestehende Interleaved-Zweig (Z. 48–62) deckt den Fall ab, der Zweig ab Z. 63 bleibt für ungepolsterte Einzel-Attribute. Kommentar mit Grund: eine `BufferAttribute` mit der gepolsterten `itemSize` zeigte dem Shader das Polster als Komponente, eine mit der Attributgröße läse das Array im falschen Raster; ein `InterleavedBuffer` trägt die Stride, und three polstert ihn nie (er hat kein `itemSize`, `WebGPUAttributeUtils.js:119`; `arrayStride` = `stride × BYTES_PER_ELEMENT`, `:306`).
  4. **`copyObjectRanges.ts`** (intern):
     ```ts
     export function copyObjectRanges(source: TypedArray, target: ThreeTypedArray, ranges: Int32Array, rangeCount: number, stride: number): void
     ```
     Kopiert für jedes der ersten `rangeCount` Paare `[from, to]` in `ranges` die Elemente `from * stride` bis `(to + 1) * stride - 1` Element für Element von `source` nach `target` (`target[e] = source[e]`), ohne `subarray()`/`set()` — der Pfad läuft jeden Frame und alloziert nichts. Die Zuweisung wandelt jeden Wert in den Elementtyp des Ziels (ein `Int8Array`-Wert `-5` landet als `-5` in einem `Int32Array`). `TypedArray` aus `./types.js`, `ThreeTypedArray` als `import type {TypedArray as ThreeTypedArray} from 'three/webgpu'`.

## Findings im Volltext

**PERF-029 · low · packages/twopoint5d/src/vertex-objects/VertexObjectBuffer.ts:178** (weitere Fundstelle `initializeAttributes.ts:69`) — Buffer-Stride auf 4 Byte ausrichten, damit three nicht bei jedem Upload neu padded

Die itemSize eines Buffers ist die Summe der Attributgrößen, ohne Ausrichtung. Ein nicht-interleavter Buffer mit einem Datentyp unter 32 Bit und einer Stride, die kein Vielfaches von 4 Byte ist (etwa uint8, uint16 oder float16 mit size 3), wird vom WebGPU-Backend von three 0.185.1 gepolstert (WebGPUAttributeUtils.js:117–125). Bei jedem Update allokiert three dafür ein neues Array in voller Länge und kopiert alle Vertices um (WebGPUAttributeUtils.js:202–212), unabhängig von den updateRanges; mit autoTouch passiert das jeden Frame. Die Descriptoren der Bibliothek selbst nutzen solche Typen nicht, die öffentliche API (`type: 'uint8'` usw.) lässt sie aber zu.

Empfehlung: Im Layout von VertexObjectBuffer die itemSize eines Buffers auf ein Vielfaches von 4 Byte aufrunden (Padding-Elemente am Ende der Vertex-Stride). Alternativ lehnt VertexObjectDescriptor solche Layouts mit einer klaren Meldung ab. Mindestens gehört es in die Doku von `type` in types.ts.

**Nebenbefund 1 · medium · packages/twopoint5d/src/vertex-objects/GeometryRoutes.ts:243** (`GeometryRoutes#syncArrays()`) — WebGPU-Update von 8-/16-Bit-Integer-Attributen ohne `normalized`

Ein Attribut vom Typ `uint8`, `uint8clamped`, `int8`, `uint16` oder `int16` ohne `normalized: true` wird unter WebGPU falsch aktualisiert: three 0.185.1 ersetzt beim Anlegen des GPU-Buffers `bufferAttribute.array` durch eine auf 32 Bit geweitete Kopie (`WebGPUAttributeUtils.js:84–109`), die Array-Synchronisierung zeigt das Attribut beim nächsten `update()` wieder auf das 8-/16-Bit-Array des Pools, und `updateAttribute()` schreibt dessen Bytes in den 32-Bit-Buffer. Vorbestehend (`git show 05d723d7:…/GeometryAttributeSlots.ts`, Z. 168), kein Descriptor der Bibliothek nutzt solche Typen. Präzisierung aus Zug 0: `uint8clamped` weitet three nicht (es prüft `constructor === Uint8Array`), der Fehler betrifft `int8`, `uint8`, `int16`, `uint16`. Nutzerentscheidung 2026-09-27: in diesem Lauf behoben, mit Test zuerst.

**Nebenbefund 2 · medium · packages/twopoint5d/src/vertex-objects/VertexObjectBuffer.ts:234–239** — Attribut-Offsets interleavter Sub-32-Bit-Buffer unter WebGPU

In einem interleavten Buffer aus `normalized` 8-/16-Bit- oder `float16`-Attributen liegt ein Attribut, dessen Vorgänger nicht auf einer 4-Byte-Grenze endet, auf einem ungeraden Byte-Offset. three 0.185.1 setzt das Attribut an Byte `offset × BYTES_PER_ELEMENT` (`WebGPUAttributeUtils.js:342`) und weitet sein Format auf ganze 4 Byte (`unorm8x4` für drei Werte, `:538–548`); WebGPU verlangt einen Offset, der ein Vielfaches von `min(4, Formatgröße)` ist, und `Offset + Formatgröße ≤ arrayStride`. Beispiel: `color` und `normal` als `uint8` normalized mit `size: 3` in einem Buffer — `normal` bei Byte 3, die Render-Pipeline wird abgelehnt, nichts wird gezeichnet. Nicht normalisierte 8-/16-Bit-Buffer betrifft es nicht (three weitet sie ganz auf 32 Bit). Vorbestehend, gefunden in Zug 0 von Paket 2b; Nutzerentscheidung 2026-09-27: Ausrichtung je Attribut in diesem Paket.
